## Final V0.1 shape

```text
Client / benchmark runner
           |
FastAPI: supported /v1/chat/completions subset
           |
Request context + absolute deadline + cancellation
           |
Bounded FIFO admission (max_inflight, max_queue, queue_timeout)
           |
Single-backend routing policy
           |
Normalized engine adapter ------> mock (local tests)
           |
           +--------------------> vLLM HTTP (cloud GPU validation)

Lifecycle events -> JSON completion logs + Prometheus metrics
Benchmark requests + correlated logs -> raw rows -> offline reports
```

This is a single-node serving gateway lab, not a distributed inference scheduler.
Gateway admission is implemented here; token-level scheduling and continuous batching
remain the engine's responsibility. V0.2 onward stays as optional future work.

## Cloud cost and measurement boundary

1. Before rental: pass CPU tests, rehearse benchmark/report commands, choose a compatible
   model and engine/container, estimate download/storage needs, and agree on the instance
   and spending limit. No automatic paid provisioning.
2. Run the gateway, benchmark client, and vLLM on the rented machine for the main baseline.
   Record process placement and resource contention. Laptop-to-cloud functional checks
   include WAN latency and must not be mixed into the co-located baseline.
3. Bind services to loopback and use SSH tunneling for access. Do not expose this
   unauthenticated gateway or inference server directly to the public internet.
4. Smoke first, then run the fixed matrix with warm-up and at least three repeats.
   Retain failed requests alongside successes.
5. Download and verify results before ending the rental. Check compute/storage charges
   and provider lifecycle rules at that time; stopping may not remove all billable resources.

Keep credentials, proxies, model weights, and private traces out of Git. Publish small,
sanitized evidence and instructions to obtain/recreate raw results; do not upload a
virtualenv, GPU environment, or model weights to GitHub.

## Collaboration and provisional estimate

The assistant handles implementation, tests, debugging, and documentation. The owner
reviews important trade-offs and evidence, approves paid resources/large downloads,
and receives a short conceptual handoff. There is no per-exercise teaching gate.

Initial estimate: **6–12 hours of owner involvement**, with **2–3 weeks of active-session
delivery time** as a planning window, not measured engineering effort or an autonomous
background schedule. Re-estimate after batch 2 and the first real-engine smoke.
Cloud rental removes the requirement to fit the final model on the local 8 GB GPU;
engine compatibility, model access, networking, and measurement quality still need verification.

The handoff covers prefill/decode, KV cache, continuous batching, admission/backpressure,
and latency/throughput trade-offs, using actual code and measurements.

## Release / resume acceptance

- JSON and SSE work through the adapter against real vLLM and a real model.
- Admission stays bounded; terminal states are unique; all tested exits release capacity.
- Gateway cleanup and verified engine-side cancellation are described separately.
- TTFT/E2E/TPOT/throughput use documented clocks, token counts, populations, and raw rows.
  Failures, repetitions, limitations, and regressions remain visible.
- A clean machine can run the mock and reproduce the real-engine instructions.
- CI actually passes remotely; publication and `v0.1.0` tagging require user direction.

Code and mock tests alone do not support all completed-tense resume claims.
